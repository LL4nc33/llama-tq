# Qwen3.8-27B — Deployment & Benchmark Log

**Model:** `Qwen3.8-27B-UD-IQ2_XXS.gguf` (9.01 GB), arch `Qwen3_5ForConditionalGeneration`
**Hardware:** RTX 2060 12 GB (sm_75, single-GPU)
**Binary:** llama-tq (TurboQuant KV) — commit noted per run
**Goal:** verify first, then optimize. Every run logged individually for reproducibility.

## Architecture facts (from research)

**Dense 27B Vision-Language model, Hybrid Attention (3:1), arch `Qwen3_5ForConditionalGeneration`.**

| Property | Value |
|----------|-------|
| Type | Dense (NOT MoE), 27.8B params |
| Layers | 64 total |
| Attention | 48× Gated DeltaNet (linear attn, NO KV-cache, fixed recurrent state) + 16× Full Attention (GQA, has KV-cache) |
| hidden_size | 5120, FFN 17408 |
| Native context | 262144 (→1M via YaRN) |
| Vision | 27-layer ViT, mmproj F16 = 0.93 GB |
| MTP | Yes (draft-mtp, max 3 draft tokens) |

**KV-cache / TurboQuant relevance — REGIME SHIFT:**
- Only 16 of 64 layers carry a classic KV-cache → KV is small by design, NOT the bottleneck.
- This leaves the proven "long-ctx = KV-bound" regime (that held for MoE-IQ2). Here the model
  is likely compute/bandwidth-bound again → TurboQuant KV leverage is architecturally limited (1/4 layers).
- llama.cpp #21385: q4_0 KV is LOSSLESS on these hybrid models (linear layers error-correct the
  quantized full-attn layers). ktq2_1/vtq2_1 (2-bit) NOT yet validated lossless here.
- **KV strategy: start q4_0 (proven lossless), then bench ktq2_1/vtq2_1 only if VRAM demands it.**

**GATED_DELTA_NET support:** Fork HAS the CUDA op (ggml_cuda_op_gated_delta_net) with multiple
kernel variants (chunking/fused/recurrent/autoregressive) — MORE than upstream master, which
merged→REVERTED the Qwen3.5 loader (#19435). We run our own implementation → verify carefully.

**Deploy strategy (research recommendation):**
1. IQ2_XXS (9.01 GB) — fits with headroom. Consider UD-IQ2_M (10.3 GB) if quality wobbles.
2. KV: q4_0 first (lossless baseline), ktq2_1/vtq2_1 second.
3. Single-GPU, no tensor split (dense → no MoE-split imbalance that OOM'd the 35B).
4. Text ctx 128-262K realistic; with vision start conservative (32-64K), measure vision-compute peak.
5. MTP: bench first — likely slower at IQ2_XXS (Q2_K regime warning), do NOT default on.

_MTP caveat: users report MTP slower than baseline at Q2_K and below — matches our own gemma4-MTP finding._

## Decisions / findings

**Run 1 (baseline):** Qwen3.8-27B loads & runs coherently on our fork (arch `qwen35`,
GATED_DELTA_NET CUDA op present with fused ar+ch variants — MORE than upstream master which
merged→reverted the loader). VRAM very relaxed vs MoE-35B: 10.1GB @ 64k q4_0, ~2GB free → vision fits.

**Speed root-cause:** 12 t/s. NOT a kernel-dispatch problem — the fused Gated DeltaNet kernel
(autoregressive + chunked) is confirmed ENABLED in the load log. This is the real fused-kernel
throughput for a dense 27B on sm_75 (all params active per token, vs MoE-35B's 3B active → ~50-60 t/s).

**Optimization axis:** since the fused GDN kernel is already active, the lever is either (a) the
GDN CUDA kernel itself is suboptimal on Turing, or (b) inherent dense-27B compute cost. Upstream
sync (649 commits behind) may carry GDN kernel perf work (chunked-optimized variant was roadmap
per research) — checking before hand-optimizing.

## DeltaNet kernel optimization analysis (in progress)

**Goal:** speed up the 12 t/s. Fused Gated DeltaNet kernel is already active (verified).
Upstream #23940 "Remove redundant CUDA copies after gated_delta_net" targets exactly our
hot kernel but does NOT cherry-pick cleanly (5 conflicts — our kernel is diverged).

**Divergence found:**
- Our fork: state snapshots written to dst-tail (`dst + attn_score_elems`), then graph copies
  to ssm_states_all via ggml_cpy. Slot: `shift = n_tokens - K; target_slot = t - shift`.
- Upstream: kernel writes state DIRECTLY into recurrent cache (`state + target_slot*stride`),
  skipping the intermediate tail write + cpy. Slot: `target_slot = n_tokens - 1 - t`.
- Also: upstream uses a `ggml_cuda_kernel_launch()` wrapper we don't have (separate concern).

**Key question under analysis:** are the two slot orderings equivalent, and can we adopt the
"write directly to recurrent cache, drop the graph cpy" optimization WITHOUT breaking our
state-snapshot semantics? The perf win is real (fewer cpy kernels, esp. at MTP K>1) but the
recurrent state MUST stay correct or the model drifts subtly over context length.

**Decision: understand fully before implementing (user directive). No blind port.**
Analysis agent running — will document semantics + a correctness-gated implementation plan.


## GDN copy-fix: PROFILED → NOT WORTH IT (evidence-based decision)

nsys GPU-kernel-time breakdown of a Qwen3.8-27B decode run (n=64, q4_0 KV, RTX 2060):

| kernel | % GPU time | what |
|--------|-----------|------|
| mul_mat_vec_q (all) | **~92%** | weight matmuls — the dense-27B compute |
| gated_delta_net_cuda | 1.4% | the DeltaNet kernel itself |
| **cpy_scalar** | **0.2%** | the copies the #23940 fix would eliminate |
| get_rows/quantize/rms_norm/ssm_conv/... | rest | minor |

**Verdict: the GDN copy-elimination rework (#23940 adapted) is NOT worth ~3h + build.**
The cpy kernels are 0.2% of GPU time; best case the whole rework saves 0.2% (less at K=1).
The 12 t/s are 92% weight-matmul bound → this is dense-27B compute on the RTX 2060, exactly
the compute/bandwidth-bound regime research predicted. The copy fix targets a non-bottleneck.

The state-slot semantics analysis (equivalent, constant stride) + the K>1 test cases we added
are kept — they are real value (the K>1 recurrent-state path was previously untested). But the
kernel rework itself is shelved: no measurable win to chase here.

**Real speed lever for this model (if ever needed):** the weight matmul path (mul_mat_vec_q) or
a fundamentally faster quant — NOT the DeltaNet copies. Or simply: this dense 27B is inherently
~12 t/s on a 2060; MoE models (3B active) are the speed play on this hardware.
